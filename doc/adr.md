<a id="adr-001"></a>
## ADR-001: 프런트엔드는 TypeScript + Vite
- 상태: 확정
- 날짜: 2026-11-18

**배경**
지도, 자동완성, 실시간 갱신이 있는 단일 페이지 웹앱이 필요하다. 정적 호스팅(ADR-003)에 올릴 수 있어야 한다.

**결정**
TypeScript와 Vite로 개발하고, 빌드 결과물(정적 파일)을 배포한다.

**결과**
- API 응답과 정류장 DB에 타입을 붙여 파싱 오류를 줄일 수 있다.
- Vite 빌드 결과는 GitHub Pages에 그대로 올릴 수 있다. 저장소 이름을 경로로 쓰므로 `base` 설정이 필요하다.
- UI 프레임워크(React/Vue/없음)는 아직 정하지 않았다. 필요하면 별도 ADR로 정한다.

<a id="adr-002"></a>
## ADR-002: 지도는 네이버 지도 JavaScript API
- 상태: 확정
- 날짜: 2026-11-18

**배경**
지도에서 정류장을 보고 클릭해서 출발지·도착지를 고를 수 있어야 한다 (FR-1.1).

**결정**
네이버 클라우드 플랫폼(NCP)의 Maps(Web Dynamic Map) API를 사용한다.

**결과**
- NCP에서 애플리케이션을 등록하고 Client ID를 받아야 한다.
- 서비스 URL(`https://<아이디>.github.io`, 개발용 `http://localhost:5173`)을 등록해야 지도가 뜬다.
- Client ID는 도메인으로 제한되므로 프런트엔드 코드에 넣어도 된다.
- 정류장이 많으므로 화면에 보이는 영역의 정류장만 표시하거나 마커를 묶어서(클러스터링) 표시해야 한다.
- 무료 사용량과 요금 조건은 NCP 가입 시 확인한다.

## ADR-003: 호스팅은 GitHub Pages
- 상태: 대체됨 → ADR-020 (2026-11-18)
- 날짜: 2026-11-18

**배경**
GitHub에서 코드를 관리하고 무료로 배포하려고 한다.

**결정**
프런트엔드 빌드 결과를 GitHub Actions로 GitHub Pages에 배포한다.

**결과**
- 비용 없이 HTTPS 주소(`https://<아이디>.github.io/<저장소>/`)를 얻는다.
- 정적 호스팅이라 서버 코드를 실행할 수 없다. 인증키 보호와 CORS 문제는 별도 프록시로 해결한다 (ADR-004).
- 정류장 DB(정적 JSON)도 같은 곳에서 제공한다 (ADR-006).

<a id="adr-004"></a>
## ADR-004: API 프록시로 Cloudflare Workers 사용
- 상태: 확정 (2026-11-18 검토 후 확정), 배포 방식과 CORS 부분은 ADR-020으로 변경
- 날짜: 2026-11-18

**배경**
- GitHub Pages는 정적 호스팅이라 브라우저가 data.go.kr을 직접 불러야 한다.
- 그러면 인증키가 브라우저 코드에 그대로 노출된다 (NFR-4 위반).
- (2026-11-18 확인) data.go.kr은 브라우저 직접 호출을 CORS로 막지 않는다. 따라서 프록시의 목적은 CORS가 아니라 키 보호와 공유 캐시다.
- 환승 검색은 정류장 여러 곳을 조회하므로 일일 호출 한도에 빨리 닿을 수 있다.

**결정**
Cloudflare Workers(무료 플랜)로 프록시를 만든다.
- 인증키는 Worker의 Secret에 저장한다.
- 브라우저는 Worker만 호출하고, Worker가 data.go.kr을 호출한다.
- 같은 정류장의 도착정보는 짧게 캐싱한다.
- CORS는 GitHub Pages 도메인과 localhost만 허용한다.
- NCP Geocoding·Reverse Geocoding도 같은 프록시로 중계한다 (ADR-013, ADR-019).
- 도착정보 캐시는 20초로 한다 (ADR-015).

**검토한 대안**
- GitHub Pages에서 브라우저가 직접 호출 (2026-11-18 재검토): data.go.kr은 다른 사이트에서의 브라우저 호출을 막지 않고(CORS 허용 확인), 네이버 주소 검색도 지도 JS API의 geocoder 모듈로 비밀키 없이 쓸 수 있어 기술적으로는 가능하다. 그러나 data.go.kr 인증키가 공개되어 다른 사람이 일일 호출 한도를 써 버릴 수 있고(텔레그램 봇도 같은 키 사용), 사용자 간 공유 캐시를 둘 수 없어 → 제외
- Vercel / Netlify Functions: 가능하지만 GitHub Pages와 따로 운영해야 하는 점은 같다. 무료 호출량과 응답 속도 면에서 Workers가 유리하다.

**결과**
- 무료 플랜: 하루 10만 요청, 요청당 CPU 10ms. Worker가 data.go.kr·네이버를 부르는 하위 요청은 요금에 세지 않는다 (2026-11-13 기준 공식 가격 문서).
- 예상 사용량(사용자 1명이 결과 화면을 1시간 켜 두면 약 360~600건)으로 보면 무료 플랜으로 충분하다. 무료 플랜에서 한도를 넘었을 때의 동작(요청 실패 여부)과 카드 등록 필요 여부는 가입 시 확인한다.
- 실제로 먼저 닿을 한도는 data.go.kr 일일 호출 한도이며, Worker의 공유 캐시가 이를 줄여 준다.
- Cloudflare 계정이 필요하다.
- 프런트엔드는 프록시 주소만 알면 된다.

<a id="adr-005"></a>
## ADR-005: 데이터는 data.go.kr 경기도 버스 API
- 상태: 확정
- 날짜: 2026-11-18

**배경**
실시간 도착 정보와 경로 탐색용 정류장·노선 데이터가 필요하다.

**결정**
공공데이터포털(data.go.kr)의 경기도 버스 API를 사용하고, 텔레그램 봇에서 쓰던 인증키를 그대로 쓴다.

| 용도 | 서비스 | 상태 |
|---|---|---|
| 실시간 도착 | 경기도_버스도착정보 조회 (`busarrivalservice/v2`) | 승인됨 |
| 정류장 목록·좌표 | 경기도_정류소 조회 (`busstationservice/v2`) | 활용신청 필요 |
| 노선 정보, 노선별 정류장 순서 | 경기도_버스노선 조회 (`busrouteservice/v2`) | 활용신청 필요 |
| 버스 위치 (선택) | 경기도_버스위치정보 조회 (`buslocationservice/v2`) | 선택 |

**결과**
- 도착정보 API만으로는 경로를 찾을 수 없으므로 정류소·노선 서비스의 활용신청이 반드시 필요하다.
- 인증키는 하나지만 서비스마다 따로 승인을 받아야 한다.
- Encoding 키가 이중 인코딩되지 않도록 처리해야 한다 (텔레그램 봇에서 겪은 403 문제).
- 서울 버스·서울 정류장은 범위에서 빠진다.

<a id="adr-006"></a>
## ADR-006: 정류장 DB는 정적 JSON, GitHub Actions로 갱신
- 상태: 확정 (2026-11-18 검토 후 확정)
- 날짜: 2026-11-18

**배경**
- 자동완성과 지도 표시를 위해 정류장 전체 목록이 브라우저에 있어야 한다 (FR-1, FR-2).
- 경로 탐색에는 노선별 정류장 순서가 필요하다.
- 무료 정적 호스팅만 쓰므로 별도 DB 서버를 두지 않는다.

**결정**
- 빌드 스크립트(Node/TypeScript)가 정류소·노선 API를 호출해 정적 JSON을 만든다.
  - `stations.json`: stationId, 정류장 번호, 이름, 좌표, 경유 노선
  - `routes.json`: routeId, 노선 번호, 정류장 순서
- GitHub Actions가 이 스크립트를 정기 실행하고(주기는 ADR-016), 바뀐 내용이 있으면 다시 배포한다. 수동으로도 실행할 수 있다.
- 브라우저는 처음 열 때 JSON을 받아 캐시하고, 자동완성 인덱스를 메모리에서 만든다.

**결과**
- 서버나 DB 비용이 없다.
- 파일 크기는 지역 범위(ADR-010)에 따라 달라진다. 크면 지역별로 나누거나 압축해서 제공한다.
- 노선 API를 노선마다 호출해야 하므로 처음 수집할 때 호출이 많다. 일일 한도를 고려해 나눠서 수집하거나 이전 결과와 비교해 바뀐 노선만 갱신한다.
- 인증키는 GitHub Actions Secret에 저장한다.

<a id="adr-007"></a>
## ADR-007: 저장은 브라우저 localStorage
- 상태: 확정
- 날짜: 2026-11-18

**배경**
선택한 출발지·도착지와 즐겨찾기 노선을 저장해야 한다 (FR-3, FR-5). 로그인 기능은 없다.

**결정**
브라우저 localStorage에 JSON으로 저장한다. 저장 형식에 버전 번호를 넣어 나중에 형식이 바뀌어도 변환할 수 있게 한다.

**결과**
- 서버가 필요 없다.
- 기기와 브라우저마다 따로 저장된다. 다른 기기와 동기화되지 않는다.
- 브라우저 데이터를 지우면 함께 지워진다.
- 사생활 보호 모드처럼 localStorage를 쓸 수 없는 경우에도 앱은 동작해야 한다(저장만 안 됨).

<a id="adr-008"></a>
## ADR-008: 탑승 시간 추정 방식
- 상태: 확정 (2026-11-18 검토 후 확정)
- 날짜: 2026-11-18

**배경**
- 경로의 도착 시각을 계산하려면 승차 정류장에서 하차(또는 환승) 정류장까지의 탑승 시간이 필요하다 (FR-4.3, FR-4.4).
- 경기도 API는 정류장 간 소요 시간을 직접 주지 않는다.
- 도착정보 API는 정류장마다 노선별 다음 버스 2대의 예측 시간과 차량번호(`plateNo1/2`)를 준다.

**결정**
아래 순서로 추정한다.
1. **차량 추적:** 내가 탈 버스의 차량번호가 하차 정류장의 도착 예측에도 나오면, 그 예측 시간을 하차 시각으로 쓴다. 가장 정확하다.
2. **구간 평균:** 1이 안 되면 (정류장 수 × 평균 구간 시간) 또는 (노선 거리 ÷ 평균 속도)로 추정한다. 평균값은 실측으로 조정한다.
3. 2번 방식으로 계산한 값은 화면에 "추정"으로 표시한다 (FR-4.6).

환승 정류장 대기 시간은 이렇게 계산한다.
- 환승 정류장 도착 시각 + 도보 시간 이후에 오는 다음 버스를 실시간 예측에서 찾는다.
- 예측 2대 안에 없으면 배차 간격으로 추정하고 "추정"으로 표시한다.

**결과**
- 하차 정류장의 도착정보를 추가로 조회해야 해서 API 호출이 늘어난다. 프록시 캐시로 줄인다 (ADR-004).
- 먼 구간은 대부분 2번 방식(추정값)이 된다.

<a id="adr-009"></a>
## ADR-009: 경로 정렬은 최종 도착 시각 우선
- 상태: 확정
- 날짜: 2026-11-18

**배경**
직행과 환승 경로를 함께 보여 줄 때 어떤 순서로 보여 줄지 정해야 한다. 요구사항: "갈아타더라도 가장 빨리 도착하는 것을 우선순위 높여 보여줘".

**결정**
- 1순위: 최종 도착 예정 시각이 빠른 순
- 2순위(도착 시각이 같을 때): 환승 횟수가 적은 순
- 3순위: 걷는 시간이 짧은 순
- 사용자는 **직행만** / **환승 포함** 모드를 고를 수 있다 (FR-4.1).

**결과**
- 환승 경로가 직행보다 빠르면 위에 나온다.
- 추정값이 들어간 경로도 같은 기준으로 정렬하되, 추정값임을 표시한다.

<a id="adr-010"></a>
## ADR-010: 서비스 지역은 성남시부터 시작
- 상태: 대체됨 → ADR-027 (2026-11-19, 경기도 전체로 확장)
- 날짜: 2026-11-18

**배경**
경기도 전체 정류장은 수만 개이고, 노선별 정류장 순서를 모으려면 노선마다 API를 호출해야 한다. 개발계정의 일일 호출 한도 안에서 처음 수집을 끝내고, DB 파일도 작게 유지하고 싶다. 지금 쓰는 정류장(판교·서현·백현)은 모두 성남시에 있다.

**결정**
- 정류장 DB는 **성남시 정류장**만 담는다.
- 노선 DB는 **성남시 정류장을 하나라도 지나는 노선**을 담는다. 노선의 정류장 순서는 성남 밖 구간까지 전체를 저장한다.
- 지역 목록은 설정값으로 두어 나중에 다른 시(용인 등)를 추가할 수 있게 한다.

**결과**
- 출발지·도착지는 성남시 정류장만 고를 수 있다.
- 노선이 성남 밖으로 나가도 경로 계산에는 노선 전체 순서를 쓴다. 다만 성남 밖 정류장은 지도와 자동완성에 나오지 않는다.
- 환승도 성남시 정류장에서만 찾는다.
- 지역을 넓히면 DB 크기와 처음 수집 시간이 늘어난다 (ADR-006).

<a id="adr-011"></a>
## ADR-011: 최대 환승은 1회
- 상태: 확정 (D-02)
- 날짜: 2026-11-18

**배경**
환승 횟수가 늘수록 경로 후보와 실시간으로 조회할 환승 정류장이 크게 늘어난다. 실시간 예측은 다음 버스 2대까지만 있어서, 환승을 여러 번 하면 뒤쪽 구간은 대부분 추정값이 된다 (ADR-008).

**결정**
경로 탐색은 **직행**과 **1회 환승**까지만 한다.

**결과**
- 경로 후보 = (출발 정류장 노선 × 도착 정류장 노선)의 공통·인접 정류장 조합이므로 미리 계산한 노선 DB만으로 빠르게 찾을 수 있다.
- 실시간 조회는 출발 정류장, 환승 정류장, (차량 추적용) 하차 정류장으로 한정된다.
- 1회 환승으로 갈 수 없는 출발지·도착지 쌍은 "경로 없음"으로 안내한다.

<a id="adr-012"></a>
## ADR-012: 환승 도보는 반경 200m까지 허용
- 상태: 확정 (D-03)
- 날짜: 2026-11-18

**배경**
실제 환승은 내린 정류장이 아니라 길 건너편이나 옆 블록 정류장에서 하는 경우가 많다. 같은 정류장만 허용하면 이런 경로를 놓친다.

**결정**
- 하차 정류장에서 **직선거리 200m 안**의 정류장을 환승 후보로 본다 (같은 정류장 포함).
- 도보 시간 = 직선거리 × 1.3(실제 보행 경로 보정) ÷ 보행 속도 1.2m/s, 최소 1분으로 계산한다.
- 계산한 도보 시간은 경로 결과에 따로 표시한다 (FR-4.4).
- 반경과 보정 계수는 설정값으로 둔다.

**결과**
- 근처 정류장 쌍(200m 이내)은 정류장 DB를 만들 때 미리 계산해 저장한다 (ADR-006).
- 도보 시간은 추정값이다. 횡단보도 신호 대기 등은 반영되지 않는다.
- 출발지·도착지가 주소·장소일 때 근처 정류장까지 걷는 구간은 ADR-013에서 다룬다.

<a id="adr-013"></a>
## ADR-013: 출발지·도착지에 주소·장소 검색 포함
- 상태: 확정 (D-04), 장소 이름 검색 부분은 ADR-019로 변경
- 날짜: 2026-11-18

**배경**
사용자는 정류장 이름을 모르는 경우가 많다. "판교역", "회사 주소"처럼 주소나 장소 이름으로 출발지·도착지를 정할 수 있어야 편하다.

**결정**
- 입력창 자동완성은 **정류장**(정류장 DB)과 **주소·장소**(네이버 API) 결과를 함께 보여 주고, 종류를 아이콘으로 구분한다.
  - 장소 이름: 네이버 검색 API의 지역 검색
  - 주소: NCP Maps의 Geocoding API
- 지도에서 정류장이 아닌 곳을 길게 누르거나 클릭해도 그 위치를 출발지·도착지로 지정할 수 있다 (좌표 → 주소 표시는 NCP Reverse Geocoding).
- 출발지·도착지가 주소·장소이면 **반경 500m 안의 정류장**을 승차·하차 후보로 쓰고, 걷는 시간을 경로 시간에 더한다. 걷는 시간 계산은 ADR-012와 같은 방식이다.
- 위 네이버 API들은 Client Secret이 필요하므로 **API 프록시(ADR-004)를 거쳐서** 호출한다.
- 주소·장소 검색은 입력이 2글자 이상이고 입력을 멈춘 뒤(약 300ms) 호출해서 호출 수를 줄인다.

**결과**
- 네이버 개발자센터(검색 API)와 NCP(Geocoding, Reverse Geocoding) 사용 신청이 추가로 필요하다.
- 프록시가 data.go.kr뿐 아니라 네이버 API도 중계하게 되므로 ADR-004를 확정해야 한다.
- 출발지·도착지 후보 정류장이 여러 개가 되어 경로 후보와 실시간 조회가 늘어난다. 후보 정류장은 가까운 순으로 개수를 제한한다(예: 각 5개).
- 서비스 지역 밖(성남시 밖, ADR-010) 주소는 "지원 지역 밖"으로 안내한다.
- 저장하는 출발지·도착지(FR-3)에는 종류(정류장/장소)와 좌표를 함께 저장한다.
- 반경 500m와 후보 개수는 설정값으로 둔다.

## ADR-014: 화면은 모바일 우선
- 상태: 확정 (D-05)
- 날짜: 2026-11-18

**배경**
버스를 기다리거나 나가기 직전에 확인하는 서비스라 주로 휴대폰에서 쓴다.

**결정**
- 휴대폰 세로 화면(폭 360~430px)을 기준으로 설계한다.
  - 지도는 화면 위쪽에, 검색·결과·즐겨찾기는 아래에서 끌어올리는 패널(바텀 시트)로 둔다.
  - 버튼과 목록 항목은 손가락으로 누르기 쉬운 크기(최소 44px)로 한다.
- 화면이 넓으면(폭 768px 이상) 왼쪽에 패널, 오른쪽에 지도를 나란히 배치한다.
- 홈 화면에 추가해서 앱처럼 열 수 있도록 웹 앱 매니페스트를 제공한다. 오프라인 기능은 범위에 넣지 않는다.

**결과**
- 결과 목록은 한 줄에 핵심 정보(도착 시각, 총 소요 시간, 환승 여부)만 보여 주고, 눌러서 상세(구간별 시간)를 펼친다.
- 지도 마커와 자동완성 목록도 터치 조작을 기준으로 만든다.

<a id="adr-015"></a>
## ADR-015: 실시간 정보 자동 갱신은 30초
- 상태: 확정 (D-06)
- 날짜: 2026-11-18

**배경**
실시간 도착 예측은 자주 바뀌지만, 너무 자주 부르면 같은 값을 다시 받으면서 일일 호출 한도만 쓴다.

**결정**
- 결과 화면이나 즐겨찾기 화면을 보고 있을 때 **30초마다** 실시간 정보를 다시 불러온다.
- 다시 불러오는 사이에는 화면의 남은 시간을 **1초마다 줄여서** 보여 준다.
- 브라우저 탭이 안 보이는 동안(백그라운드)은 갱신을 멈추고, 다시 보이면 바로 갱신한다.
- 수동 새로고침 버튼은 언제든 쓸 수 있다. 다만 프록시 캐시 때문에 같은 정류장은 최대 20초 동안 같은 값이 나올 수 있다.
- 프록시의 도착정보 캐시는 **20초**로 한다 (ADR-004).

**결과**
- 사용자 한 명이 화면을 켜 두면 정류장당 분당 2회 정도 호출한다. 여러 사람이 같은 정류장을 보면 프록시 캐시 덕분에 호출이 늘지 않는다.
- 마지막 갱신 시각을 화면에 표시한다.

## ADR-016: 정류장 DB는 매주 자동 갱신 + 수동 실행
- 상태: 확정 (D-07)
- 날짜: 2026-11-18

**배경**
노선 개편이나 정류장 신설은 자주 일어나지 않는다. 반면 노선별 정류장 순서를 모으려면 노선마다 API를 불러야 해서, 매일 수집하면 일일 호출 한도를 많이 쓴다.

**결정**
- GitHub Actions로 **매주 1회**(월요일 새벽, 한국 시간 03:00) 정류장·노선 데이터를 다시 수집한다.
- GitHub 화면에서 **수동 실행**(workflow_dispatch)도 할 수 있게 한다.
- 수집 결과를 이전 데이터와 비교해 **바뀐 내용이 있을 때만** 커밋하고 다시 배포한다.
- 수집이 실패하거나 결과가 비정상적으로 작으면(예: 정류장 수가 이전보다 20% 넘게 줄면) 기존 데이터를 유지하고 실패로 표시한다.

**결과**
- 노선 개편은 최대 1주일 늦게 반영될 수 있다. 급하면 수동으로 실행한다.
- 데이터에 수집 날짜를 넣어 화면에 "정류장 정보 기준일"로 표시한다.
- GitHub Actions 무료 사용량 안에서 충분히 돌아간다.

<a id="adr-017"></a>
## ADR-017: 즐겨찾기는 경로 전체 단위
- 상태: 확정 (D-08)
- 날짜: 2026-11-18

**배경**
추천 결과에서 고른 노선을 즐겨찾기로 저장해야 한다 (FR-5). 환승 경로는 노선이 2개이고 승차·환승·하차 정류장이 각각 다르다.

**결정**
- 즐겨찾기 하나 = **경로 하나 전체**: 출발지 → (승차 정류장, 노선) → [환승 정류장, 노선] → 하차 정류장 → 도착지.
  - 예: "판교 → 서현: 32번 → 백현마을1단지 환승 → 103번"
- 즐겨찾기를 누르면 그 경로만 실시간으로 다시 계산해서 보여 준다.
  - 각 구간의 실시간 도착 예정 시간
  - 환승 대기 시간, 최종 도착 예정 시각
- 이름을 바꿀 수 있다 (예: "출근").
- 저장 형식에는 stationId, routeId와 표시용 이름·번호를 함께 넣는다. 노선이 없어지는 등 DB에서 찾을 수 없게 되면 "노선 정보가 바뀌었습니다"로 표시한다.

**결과**
- 즐겨찾기 화면에서 경로마다 "다음 출발 가능 시각"과 "도착 예정 시각"을 한 줄로 보여 줄 수 있다.
- 같은 출발지·도착지의 다른 경로와 비교하려면 저장된 출발지·도착지 쌍(FR-3)으로 다시 검색한다.

## ADR-018: 웹서비스는 새 GitHub 저장소에 둔다

**배경**
기존 `C:\Claude\mybus` 폴더에는 텔레그램 봇 코드와 `.env`(실제 키)가 있고, git 저장소가 아니다. 웹서비스는 GitHub Pages로 공개 배포한다 (ADR-003).

<a id="adr-019"></a>
## ADR-019: 네이버 검색 API는 쓰지 않고 주소 검색만 사용
- 상태: 확정 (ADR-013 일부 변경)
- 날짜: 2026-11-18

**배경**
ADR-013에서는 장소 이름 검색에 네이버 검색 API(지역 검색)를 쓰기로 했다. 신청하고 관리할 API를 줄이기 위해 이 API는 쓰지 않기로 했다.

**결정**
- 네이버 검색 API(지역 검색)는 사용하지 않는다.
- 입력창 자동완성은 **정류장**(정류장 DB)과 **주소**(NCP Geocoding) 두 가지만 보여 준다.
- 지도에서 위치를 눌러 지정하는 기능(NCP Reverse Geocoding)과 근처 500m 정류장 검색, 도보 시간 계산은 ADR-013대로 유지한다.

**결과**
- "스타벅스 판교점", "회사 이름" 같은 **장소 이름으로는 검색되지 않는다.** 이런 곳은 주소로 검색하거나 지도에서 직접 눌러야 한다.
- 다만 "판교역", "서현역", "분당구청"처럼 **정류장 이름에 들어 있는 장소**는 정류장 자동완성으로 찾을 수 있다.
- 신청할 API에서 네이버 개발자센터(검색 API)가 빠진다. NCP Maps(지도, Geocoding, Reverse Geocoding)만 있으면 된다.
- NCP Geocoding은 도로명·지번 주소 입력에 맞춰져 있으므로, 자동완성은 입력이 주소 형태일 때(예: 숫자나 "로/길/동"이 들어 있을 때) 우선으로 호출한다.

<a id="adr-020"></a>
## ADR-020: 웹 화면과 API를 모두 Cloudflare Workers 하나로 배포
- 상태: 확정 (ADR-003 대체, ADR-004 일부 변경)
- 날짜: 2026-11-18

**배경**
ADR-003은 웹 화면을 GitHub Pages에, ADR-004는 API 프록시를 Cloudflare Workers에 두는 구성이었다. 배포 위치가 두 곳이라 관리할 곳이 많고, 서로 다른 주소라 CORS 설정이 필요했다. Cloudflare Workers는 정적 파일 제공이 무료이고 요청 수 제한도 없다.

**결정**
- Worker 하나(`mybus-route`)가 **웹 화면(정적 파일)과 API를 함께** 제공한다.
  - `/api/*` 요청은 Worker 코드가 처리한다 (도착정보, Geocoding).
  - 나머지 요청은 `web/dist`의 정적 파일로 응답한다 (Workers Static Assets).
- 웹과 API가 같은 주소를 쓰므로 **CORS 설정을 없앤다.** 로컬 개발에서는 Vite 개발 서버가 `/api`를 로컬 Worker로 넘긴다.
- 배포는 Cloudflare의 **Workers Builds**를 GitHub 저장소에 연결해서 `main`에 push할 때마다 자동으로 한다. GitHub Pages 배포 워크플로는 지운다.
- GitHub 저장소는 코드 보관용이며 **Public을 유지**한다 (2026-11-18 결정). 나중에 Private으로 바꿔도 배포에는 영향이 없다.

**결과**
- 서비스 주소: `https://mybus-route.<Cloudflare 계정 서브도메인>.workers.dev` (나중에 도메인을 붙일 수 있다).
- 네이버 지도(NCP) 서비스 URL에는 위 주소와 `http://localhost:5173`을 등록한다 (ADR-002).
- Vite `base`는 `/`가 된다 (ADR-001).
- 네이버 지도 Client ID는 빌드할 때 넣으므로 Workers Builds의 빌드 변수(`VITE_NAVER_MAP_CLIENT_ID`)로 등록한다.
- 정류장 DB 주간 갱신(ADR-016)은 계속 GitHub Actions로 실행하고, 결과를 커밋하면 Workers Builds가 다시 배포한다.
- 정적 파일 요청은 무료이고 Worker 요청 수(하루 10만)에 세지 않는다. `/api/*` 요청만 센다.

## ADR-021: 화면 분위기는 미니멀 화이트
- 상태: 확정
- 날짜: 2026-11-19

**배경**
기능 검증용으로 만든 첫 화면은 정보가 많고 정리되지 않았다. 출퇴근길에 한눈에 읽히는 깔끔한 화면이 필요하다.

**결정**
- 흰 배경, 연한 회색 카드, 넓은 여백, 포인트 색 하나를 쓴다.
- 가장 중요한 숫자(도착 시각, 남은 분)를 굵고 크게, 나머지는 작고 흐리게 한다.
- 노선 번호는 노선 종류 색(마을·일반·직행 등)을 작은 배지로만 쓰고 화면 전체 색은 절제한다.
- 다크 모드는 같은 구조에서 색만 바꾼다.

**결과**
- 디자인 토큰(색·글자 크기·간격·모서리)을 CSS 변수로 정리하고 모든 화면이 그것만 쓰게 한다.

## ADR-022: 첫 화면은 즐겨찾기 카드
- 상태: 확정
- 날짜: 2026-11-19

**배경**
대부분 같은 경로(출근·퇴근)를 반복해서 본다. 앱을 열자마자 다음 버스와 도착 시각이 보여야 한다.

**결정**
- 첫 화면 순서: 날씨 한 줄(ADR-024) → 즐겨찾기 카드 → 작은 검색 입력 → 최근 검색.
- 즐겨찾기 카드마다 실시간으로 "다음 출발 n분 후 · 도착 HH:MM"을 보여 준다 (30초 갱신, ADR-015).
- 카드를 누르면 그 경로의 상세(시간 막대, 구간별 정보)로 들어간다.
- 즐겨찾기가 없으면 검색 입력을 크게 보여 주고 "자주 가는 경로를 즐겨찾기 해 보세요" 안내를 둔다.
- 지도는 검색·상세 화면에서 보여 준다.

**결과**
- 첫 화면에서 즐겨찾기 수만큼 경로를 실시간 평가하므로 API 호출이 늘어난다. 즐겨찾기 카드는 화면에 보일 때만 갱신한다.

## ADR-025: 화면은 React로 만든다
- 상태: 확정 (ADR-001 보완)
- 날짜: 2026-11-19

**배경**
리디자인(ADR-021~024)으로 홈·검색·상세 3개 화면과 즐겨찾기 카드, 시간 막대 같은 반복 요소가 생긴다. 순수 TypeScript로 DOM을 직접 다루면 화면이 늘수록 상태 관리가 복잡해진다. fullstack-webapp 하네스도 React 컴포넌트 패턴을 전제로 한다.

- 스타일은 CSS 변수 디자인 토큰(ADR-021)으로 하고 Tailwind 는 쓰지 않는다.

**결과**
- 의존성이 react, react-dom 으로 늘어난다.
- 네이버 지도는 React 컴포넌트로 감싼다.

## ADR-026: 날씨 위치는 기본 성남시청, 고른 출발지·도착지 기준
- 상태: 확정 (ADR-024 보완)
- 날짜: 2026-11-19

**배경**
경기도 전체로 넓히면(ADR-027) 한 곳의 날씨로는 부족하다. 사용자는 출발지와 도착지 날씨를 알고 싶다.

**결정**
- **홈**: 기본 위치 **성남시청**(37.4200, 127.1267, 기상청 격자 62·124) 날씨를 "성남시청" 라벨과 함께 보여 준다.
- **검색·상세**: 고른 **출발지·도착지** 위치의 날씨를 보여 준다.
  - 두 곳이 같은 기상청 격자(약 5km)면 한 줄("출발·도착"), 다르면 두 줄("출발", "도착").
  - 하나만 골랐으면 그 위치, 아무것도 안 골랐으면 기본 위치.
- Worker `/api/weather`의 기본 좌표도 성남시청으로 바꾼다.
- 격자 비교를 위해 기상청 격자 변환식을 웹에도 둔다 (Worker 와 같은 식, 테스트로 일치 확인).

**결과**
- 검색 화면에서 날씨 요청이 최대 2개 늘어난다. Worker 10분 캐시와 브라우저 메모리 캐시로 완화된다.

<a id="adr-027"></a>
## ADR-027: 서비스 지역을 경기도 전체로 확장하고, 버스기반정보 파일로 수집한다
- 상태: 확정 (ADR-010 대체, ADR-006 수집 방식 변경) — 2026-11-19 구현
- 날짜: 2026-11-19

**배경**
- 성남시 외 지역도 쓰고 싶다.
- 지금 수집 방식(정류장 → 경유노선 → 노선 정류장 순서, ADR-006)은 정류장마다 API 를 부른다. 개발계정 정류소 조회는 하루 약 1,000건이라 경기도 정류장(수만 곳)을 모으는 데 한 달 이상 걸린다.
- 경기버스정보(GBIS)는 **기반정보 서비스**(`baseinfoservice/v2/getBaseInfoItemv2`)로 경기도 전체 정류소·노선·노선-정류소 파일의 다운로드 주소를 매일 제공한다. API 호출은 1번이면 된다.

**결정**
- 수집 스크립트(`scripts/build-db.ts`)를 기반정보 파일 방식으로 바꾼다.
  - 정류소 파일(`station…V2.txt`): stationId, mobileNo, 이름, 좌표, 지역명
  - 노선 파일(`route…V2.txt`): 번호, 유형, 첫차·막차, 배차, 회차 순번
  - 노선-정류소 파일(`routestation…V2.txt`): 노선별 정류장 순서
- 출발지·도착지·환승 정류장은 **경기도 전체**로 넓힌다 (ADR-010의 "성남시 정류장만" 제한을 없앤다).
- 파일이 커지므로(정류장 수만 곳, 노선 수천 개) 웹에 내려보내는 JSON 은 압축된 형식으로 만든다. 구체적인 형식(정류장 번호 대신 인덱스, 지역별 분할 여부 등)은 실제 파일 크기를 보고 정한다.
- 날씨는 ADR-026 을 따른다.

**결과**
- data.go.kr 에서 **경기도_버스기반정보 조회** 활용신청이 필요하다 (2026-11-19 현재 미등록).
- 정류장 DB 갱신(ADR-016)이 매주 API 수백~천 건에서 1건 + 파일 다운로드로 줄어든다.
- 데이터 크기와 경로 탐색 성능을 다시 확인해야 한다 (모바일에서 첫 로딩 시간).
- 서울 정류장은 여전히 포함되지 않는다 (경기도 버스가 서울을 지나는 구간은 노선 데이터에 포함).

**구현 결과 (2026-11-19)**
- 기반정보 파일은 UTF-8, 레코드 구분 `^`, 필드 구분 `|`, 첫 레코드가 헤더다.
- 2026-11-19 버전: 정류소 46,143곳(노선에 쓰이는 곳 41,052곳, 그중 경기도 31개 시군 + 정류장 번호가 있어 고를 수 있는 곳 38,292곳), 노선 3,160개, 노선-정류소 198,410행.
- 웹 데이터 형식 v2: 열 이름 + 행 배열, 노선의 정류장은 정류장 배열 인덱스. `stations.json` 2.7MB(gzip 0.7MB), `routes.json` 1.3MB(gzip 0.36MB). 지역별 분할은 하지 않았다 (한 번 받으면 브라우저 캐시).
- 측정(개발 PC, Node): 색인 만들기 약 0.27초, 경로 후보 탐색 약 20ms. 판교 → 수원시청은 4000번 직행·환승 경로를 찾는다. 성남시청 → 의정부시청처럼 1회 환승으로 안 되는 장거리는 "경로 없음"이다 (ADR-011).
- ADR-016 매주 자동 갱신(GitHub Actions)은 아직 만들지 않았다. 지금은 `npm run build:db` 를 직접 실행한다.

<a id="adr-028"></a>
## ADR-028: 노선 번호를 누르면 노선 정보 화면 (기본정보 + 운행 중 버스 위치)
- 상태: 확정 (2026-11-19 버스위치정보 승인, 실데이터 확인)
- 날짜: 2026-11-19

**배경**
경로 결과에서 버스 번호를 보고 그 노선이 어디서 어디로 가는지, 몇 분마다 오는지, 지금 버스들이 어디쯤 있는지 알고 싶다.

**결정**
- 노선 번호 배지를 누르면 **노선 정보 화면**(`#bus/<노선ID>[/<정류장ID>]`)을 연다.
  - 누를 수 있는 곳: 상세 화면의 단계 목록, 출발 정류장 실시간 도착판. 결과 카드·즐겨찾기 카드는 카드 전체가 버튼이라 배지를 따로 누를 수 없다(버튼 안에 버튼 금지) — 카드 → 상세에서 누른다.
- **기본정보** (정적 데이터, 버스기반정보 노선 파일):
  - 기점 ↔ 종점(회차 정류장), 기점 출발 첫차~막차, 종점 출발 첫차~막차
  - 배차 간격(출퇴근·평시), 운수회사·전화, 운행 지역
  - **총 보유 대수는 공개 데이터에 없다.** 대신 지금 **운행 중인 버스 수**(방향별)를 보여 준다.
- **운행 중 버스 위치** (실시간): Worker `/api/bus-locations?routeId=` → data.go.kr 경기도_버스위치정보 조회(`getBusLocationListv2`). 15초 캐시, 6초 타임아웃. 화면은 15초마다 갱신(화면이 보일 때만).
  - 정류장 목록을 **기점 → 종점**(상행), **종점 → 기점**(하행) 두 구간의 세로 노선도로 그리고, 버스가 있는 정류장에 차량번호·상태(도착/출발/교차로 통과)·저상·혼잡도·빈자리를 표시한다.
  - 들어온 정류장(`정류장ID`)은 "내 정류장"으로 강조하고 그 위치로 스크롤한다.
- routes.json(v2)에 종점 첫·막차, 운수회사, 전화, 운행 지역 열을 추가한다.

**결과**
- 활용신청 전에는 기본정보와 노선도만 보이고 "버스위치정보 서비스 활용신청이 필요합니다"를 안내한다.
- 지도에 노선 경로와 버스를 그리는 것은 범위에 넣지 않았다 (필요하면 노선 형상 파일 routeline 으로 확장).

## ADR-029: 지도 경로는 노선 형상(도로를 따라가는 선)으로 그린다
- 상태: 확정
- 날짜: 2026-11-19

**배경**
지도의 버스 경로가 정류장 좌표를 직선으로 이어 도로를 벗어나 보였다. 노선 정보 화면의 버스도 도로 위에 있어야 자연스럽다.

**결정**
- 경기도 버스기반정보의 **노선 형상 파일**(`routeline…V2.txt`, 약 100MB, 250만 점)을 `scripts/build-shapes.ts`로 가공한다.
  - 노선별로 나누고 Douglas–Peucker 로 약 4m 허용 단순화 (250만 → 87만 점)
  - 정류장마다 형상의 몇 번째 점인지 앞으로만 찾아 기록 (왕복 노선에서 반대편에 붙지 않게)
  - `web/public/data/lines/<노선ID>.json` (1e5 정수 차이 인코딩, 노선당 약 2KB, 전체 약 7MB)
- 웹은 **필요한 노선의 형상만** 받는다. 받기 전·실패 시에는 정류장 직선을 먼저 보여 준다.
  - 검색·상세: 승차~하차 구간만 잘라 그린다.
  - 노선 정보 화면: 노선 전체를 그리고 운행 중 버스를 도로 위에 표시한다. 정류장 도착이면 정류장에, 출발·교차로 통과면 다음 정류장 쪽 도로 위에 둔다.
- `npm run build:db` 가 정류장·노선 데이터와 형상을 함께 만든다.

**결과**
- 배포 파일이 노선 수만큼(약 3,160개) 늘어난다 (Cloudflare 정적 파일 한도 2만 개 안).
- 버스 위치는 정류장 단위 정보라 "도로 위 정확한 위치"는 아니다. 정류장 사이 대략적 위치로 표시한다.

<a id="adr-030"></a>
## ADR-030: 내 위치를 출발지로 쓰고, 움직이면 따라간다
- 상태: 확정
- 날짜: 2026-11-19

**배경**
걸어가면서 앱을 보면 출발지가 계속 바뀐다. 매번 주소를 다시 입력하지 않고 현재 위치에서 가장 빠른 버스를 보고 싶다.

**결정**
- 검색 화면의 **"📍 내 위치에서 출발"** 버튼으로 브라우저 위치(Geolocation)를 받아 출발지를 "내 위치"로 정한다.
- 출발지(또는 도착지)가 내 위치이면 검색 화면이 보이는 동안 `watchPosition`으로 위치를 계속 받는다.
  - **30m 넘게 움직였을 때만** 출발지를 옮기고 경로·근처 정류장·도착판을 다시 계산한다 (GPS 흔들림과 과도한 API 호출 방지).
  - 탭이 안 보이거나 검색 화면을 떠나면 추적을 멈춘다 (배터리).
- 지도에서는 출발 핀을 "나"로 표시한다.
- 최근 검색에는 좌표와 상관없이 "내 위치" 항목 하나로 저장한다. 다시 누르면 저장된 좌표로 시작해 바로 현재 위치로 갱신한다.
- 위치 권한 거부·실패 시 이유를 안내하고 다른 입력은 그대로 쓸 수 있다.
- 위치 정보는 브라우저 안에서만 쓰며 서버로 보내지 않는다 (경로 탐색은 브라우저에서, 날씨는 소수 3자리로 반올림한 좌표만 Worker 로).

**결과**
- HTTPS(배포 사이트)와 localhost 에서만 동작한다.
- 상세 화면은 고른 경로를 그대로 보여 주므로 추적하지 않는다. 걷는 중 더 빠른 경로가 생기면 검색 화면에서 보인다.

<a id="adr-031"></a>
## ADR-031: 노선 정보 화면 — 상·하행 좌우 배치, 30초 갱신, 정류장 사이 위치 추정
- 상태: 확정 (ADR-028 보완)
- 날짜: 2026-11-19

**배경**
상행·하행을 위아래로 이어 놓으니 길어서 한눈에 보기 어려웠다. 버스가 정류장 단위로만 뚝뚝 옮겨져 실제로 움직이는 느낌이 없었다.

**결정**
- **상행(기점→종점)과 하행(종점→기점)을 좌우 두 열**로 나란히 놓는다. 휴대폰(375px)에서도 두 열, 열 제목은 스크롤해도 위에 붙어 있다.
- **30초마다** 버스 위치를 다시 받는다 (Worker 캐시 20초). 2026-11-19 사용자 요청으로 10초 → 30초로 되돌림. 그사이에는 아래 추정으로 버스를 계속 움직인다.
- **정류장 사이 위치 추정**: API 는 "몇 번째 정류장 + 도착/출발/교차로 통과"만 준다.
  - 차량번호별로 그 상태를 처음 본 시각을 기억하고, 진행률 = 시작값 + 지난 시간 × 평균 속도(6m/s) ÷ 다음 정류장까지 **도로 거리**(노선 형상, ADR-029).
  - 시작값: 출발 0.05, 교차로 통과 0.35(구간 중간쯤), 도착은 정류장 위(0). 다음 정류장 도착 신호 전에는 최대 0.92 까지만.
  - 1초마다 다시 계산해 노선도의 정류장 사이 칸과 지도에서 버스를 조금씩 앞으로 옮긴다. 30초마다 실제 값이 오면 바로잡는다.
  - 노선도의 정류장 사이 칸에 "다음까지 약 n m"를 표시한다.

**결과**
- 정류장 사이 위치는 **추정**이다 (실제 GPS 좌표가 아님). 화면에 그렇게 안내한다.
- 데이터 호출은 30초 간격 (화면이 보일 때만, Worker 캐시 공유).

## ADR-032: data.go.kr 일일 호출 한도 대응 — 호출 줄이기, 한도 안내, 사용량 기록
- 상태: 확정
- 날짜: 2026-11-19

**배경**
2026-11-19 밤 경기도_버스도착정보 조회가 **일일 호출 한도 초과**(resultCode 22)로 막혀 모든 경로가 "실시간 정보를 가져오지 못했습니다"가 되었다. 버스위치 서비스는 정상이었다(서비스별 한도).
- 검색 한 번이 후보 정류장을 많게는 25곳 가까이 조회했고, 30초마다 같은 수를 다시 불렀다.
- `workers.dev` 에서는 Cloudflare 캐시가 동작하지 않아(ADR-004 보완) 공유 캐시 효과가 적다.
- 그날 개발·테스트로도 많이 불렀다.

**결정**
1. **호출 줄이기**
   - 후보 수: 직행 8 → 6, 환승 10 → 6.
   - 첫 평가만 후보 전체, **30초 자동 갱신은 위쪽 결과 4개만** 다시 평가한다. 나머지는 이전 값으로 카운트다운. ↻ 수동 새로고침은 전체.
   - 측정(실제 경기도 데이터): 07015→07147 첫 평가 6회·갱신당 최대 4회, 판교→수원시청 9회·6회 (+ 출발 정류장 도착판 1회).
2. **한도 안내**: Worker 가 일일 한도(초당 제한과 구분)를 알아채면 재시도하지 않고 `429 {code: DAILY_LIMIT}` 를 돌려주고, **10분 동안 data.go.kr 을 다시 부르지 않는다**. 화면은 "오늘 실시간 조회 한도를 모두 썼습니다 … 자정 이후 다시 됩니다"를 보여 주고 '다시 시도' 버튼은 숨긴다.
3. **사용량 기록**: Worker 가 API 요청마다 `{api, id, screen, status, cache, ms}` 한 줄을 남긴다 (Workers Logs, `[observability]`). 웹은 `X-Screen`(home/search/detail/fav/bus) 헤더를 보낸다. 위치·주소는 남기지 않는다.

**결과**
- 정확한 일일 사용량과 한도는 data.go.kr 마이페이지에서 확인한다. 개발계정 한도가 부족하면 **운영계정 신청(활용사례 등록)** 으로 늘린다.
- 사용량 기록으로 어느 화면이 많이 부르는지 Cloudflare 대시보드에서 볼 수 있다.

## ADR-033: ☰ 메뉴와 개인위치정보 처리방침, 위치정보는 최소한으로만 내보낸다
- 상태: 확정
- 날짜: 2026-11-19

**배경**
"내 위치"(ADR-030)를 쓰므로 위치정보를 어떻게 다루는지 이용자에게 알려야 한다. 또 아이폰 Safari 에서 사이트 설정이 "묻기"인데도 허용 팝업 없이 거절되는 경우가 있었다.

**결정**
- **모든 화면 오른쪽 위 ☰ 버튼** → 메뉴 → **개인위치정보 처리방침** 화면(`#privacy`). 메뉴는 바깥을 누르거나 Esc 로 닫힌다. 상단 바는 오른쪽을 비워 ☰ 와 겹치지 않게 한다.
- 처리방침에는 수집 항목·방법, 이용 목적, 기기 밖으로 나가는 정보(표), 보관·파기, 이용자 권리, 8세 이하 아동, 변경 안내를 담는다. 위치정보 관리책임자·문의 항목은 2026-11-19 사용자 요청으로 일단 뺐다 (필요해지면 다시 넣는다).
- **위치정보 최소 전송**
  - 날씨는 브라우저에서 위치를 **기상청 격자 번호(약 5km)** 로 바꿔 `nx, ny` 만 보낸다. 내 위치 좌표는 서버로 가지 않는다.
  - Worker 로그는 코드가 남기는 한 줄(기능, 정류장·노선 번호, 화면, 상태, 캐시, 시간)만 보관하고, 요청 주소가 남는 자동 요청 기록(`invocation_logs`)은 끈다 — 주소 검색어·지도에서 고른 좌표가 로그에 남지 않게.
- **아이폰 즉시 거절 구분**: 위치 요청이 0.7초 안에 거절되면 팝업이 뜨지 않은 것으로 보고("기기 설정에서 브라우저의 위치 사용이 꺼져 있을 수 있습니다"), 기기별 허용 방법을 보여 준다. iOS 안내에는 "설정 → 위치 서비스 → Safari 웹 사이트가 '안 함'이면 사이트 설정이 '묻기'여도 거절된다"를 넣는다.

**결과**
- 처리방침 내용은 앱 동작이 바뀌면 함께 고쳐야 한다 (ADR 와 같이 관리).
- 법적 요건(위치기반서비스사업 신고 등)은 서비스 규모·공개 범위에 따라 별도로 확인한다.

<a id="adr-034"></a>
## ADR-034: 새 버전 알림과 버전 표시
- 상태: 확정
- 날짜: 2026-11-19

**배경**
배포 후에도 이용자 브라우저에서 이전 화면이 보였다. 서버는 최신 빌드를 주고 있었고 `index.html` 도 캐시하지 않는다(`max-age=0, must-revalidate`, 서비스 워커 없음). 열어 둔 탭이나 아이폰 "홈 화면에 추가" 앱은 다시 불러오기 전까지 예전 코드를 계속 실행하기 때문이다.

**결정**
- 빌드마다 `version.json`(`{build: 빌드 시각}`)을 만들고, 화면에도 같은 값을 넣는다.
- 화면이 다시 보일 때와 10분마다 `version.json` 을 캐시 없이 읽어 다르면 아래에 **"새 버전이 나왔습니다 [새로고침]"** 을 띄운다. 자동으로 새로고침하지는 않는다 (입력 중인 내용을 지키기 위해).
- ☰ 메뉴 맨 아래에 **버전(빌드 시각, 한국 시간)** 을 보여 줘 지금 화면이 최신인지 확인할 수 있게 한다.

**결과**
- 이 기능이 들어간 버전부터 적용된다. 그 전 버전을 열어 둔 화면은 한 번은 직접 새로고침해야 한다.

<a id="adr-035"></a>
## ADR-035: 호출 점검 — 내 위치는 한 번만, 쉬면 자동 갱신 멈춤, 불필요한 호출 제거
- 상태: 확정 (ADR-030 일부 변경, ADR-032 보완)
- 날짜: 2026-11-20

**배경**
data.go.kr 일일 한도(ADR-032) 이후 "버스 조회가 너무 많지 않은지" 내부 점검을 했다.

**점검 결과 (호출하는 곳과 주기)**
| 화면 | 무엇을 | 주기 |
|---|---|---|
| 홈 | 즐겨찾기 전부 (경로당 정류장 2~3곳) | 30초 |
| 검색 | 위쪽 결과 4개(정류장 4~6곳) + 출발 정류장 도착판 1곳 | 30초 (첫 검색 6~9곳) |
| 상세 | 고른 경로 1개 (2~4곳) | 30초 |
| 노선 | 버스 위치 (별도 서비스) | 30초 |
| 날씨 | 화면당 1~2곳 | 10분 캐시 |
모든 화면은 탭이 안 보이면 멈추고, 상세 화면 뒤에 숨은 검색 화면도 멈춘다.

**찾은 낭비**
1. 화면을 **켜 둔 채 두면 30초마다 끝없이** 조회한다 — 검색 화면 1시간이면 600~800건.
2. 다른 앱에 갔다 오거나 상세에서 돌아올 때마다 **방금 갱신했어도 다시 전체 조회**했다.
3. "내 위치" 실시간 추적이 30m 움직일 때마다 경로·도착판을 다시 조회했다.
4. 정류장 번호(예: 07015)를 칠 때마다 **주소 검색(NCP)** 도 불렀다.
5. 날씨 브라우저 캐시가 좌표 단위라 같은 5km 칸도 다시 불렀다.

**결정**
1. **5분 동안 조작이 없으면 자동 갱신을 멈춘다** ("자동 갱신 멈춤 (화면을 누르면 다시 시작)"). 누르면 오래된 경우 바로 갱신하고 이어서 30초마다.
2. 화면이 다시 활성화되면 **마지막 갱신 후 30초가 지났을 때만** 갱신한다. 새 검색(경로 후보가 바뀜)일 때만 바로 조회.
3. **내 위치는 버튼을 누를 때 한 번만** 받는다. 계속 따라가지 않는다 (ADR-030 의 실시간 추적 중단). 버튼은 "내 위치 다시 찾기"로 바뀐다.
4. 숫자만 입력하면 정류장 번호로 보고 주소 검색을 하지 않는다.
5. 날씨 브라우저 캐시 키를 기상청 격자로 바꾼다.
- 덤: 노선 화면에서 지도를 움직이면 1초마다 원래 위치로 돌아가던 문제를 고쳤다 (같은 출발 핀을 매번 새로 넘겨 지도가 다시 이동하던 것).

**결과**
- 켜 둔 화면이 하루 한도를 다 쓰는 일은 최대 5분 + 1회로 줄어든다.

## ADR-036: 노선 화면에서 정류장을 누르면 지도에서 그 정류장을 보여 준다

- **결정**: 노선도의 정류장 이름(예: "성남역.보평중고등학교 07557")을 버튼으로 바꾼다. 누르면 지도를 그 정류장으로 옮기고(줌 17 미만이면 17로 확대) 강조 점과 이름표를 띄운다. 지도가 화면 밖에 있으면 지도가 보이게 스크롤한다. 고른 정류장은 목록에서도 강조한다.
- **구현**: `MapView.showStop`이 강조 마커를 하나만 유지한다. `NaverMap`의 `focusStop` prop은 누를 때마다 올라가는 `n`이 바뀔 때만 지도를 옮긴다. 그래서 30초 갱신으로 화면이 다시 그려져도 사용자가 옮긴 지도를 되돌리지 않는다(ADR-035의 endpointKey와 같은 원칙).
- **호출**: 추가 API 호출은 없다. 정류장 좌표는 로컬 DB에서 가져온다.

## ADR-037: 노선 선을 도로 오른쪽으로 그린다

- **배경**: 형상 데이터는 도로 가운데를 따라가서, 왕복 노선이 같은 도로를 지나면 가는 선과 오는 선이 겹친다. 버스는 실제로 오른쪽 차로로 다닌다.
- **결정**: 지도에 그리는 노선·경로 선을 진행 방향 오른쪽으로 4px(선 두께 5px) 옮겨 그린다. 화면 픽셀 기준이라 확대 단계가 바뀌면(`zoom_changed`) 다시 계산한다. 그래서 어느 줌에서나 선이 도로 오른쪽에 붙어 보이고, 같은 도로의 상행·하행 선이 나란히 보인다.
- **구현**: `lib/offset.ts`의 `offsetRight`는 평면 근사에서 선분 법선의 평균 방향으로 옮긴다. 꺾이는 곳은 마이터 방식으로 옮기되 2배까지만 늘린다. `metersPerPixel`은 256px 타일 웹 메르카토르 기준이다.
- **범위**: 선만 옮긴다. 버스·정류장 마커는 원래 좌표에 둔다.

## ADR-038: 추천 목록을 보며 키패드만 내리기, 버스 번호로 노선 바로 보기

- **키패드 내리기**: 휴대폰에서 출발지·도착지를 입력하면 키패드가 추천 목록을 가린다. 지금까지는 입력에서 포커스가 빠지면(blur) 목록도 닫혀서 목록만 볼 방법이 없었다.
  - 목록 맨 위에 "추천 N개 · 키패드 내리기 ⌄" 버튼을 둔다(입력 중일 때만).
  - 목록을 스크롤해도 키패드를 내린다.
  - 이렇게 내렸을 때는 목록을 유지하고, 입력과 목록 바깥을 누르면 닫는다.
- **노선 바로 보기**: 홈에 "버스 노선 바로 보기" 입력을 둔다.
  - 번호(대소문자·공백·하이픈 무시)로 노선을 찾는다. 순서는 정확 일치 → 앞부분 일치 → 중간 일치이며, 같은 순위면 짧은 번호와 운행지역 순이다.
  - 같은 번호가 여러 시에 있어서(예: "1" 20개) 기점→회차점과 운행지역을 함께 보여 준다.
  - 누르면 노선 정보 화면(ADR-028)으로 간다.
  - 결과는 입력 아래에 펼쳐서 키패드를 내려도 남는다. 완료 키와 목록 스크롤로 키패드가 내려간다.
- **호출**: 노선 검색은 로컬 DB만 쓰며 API를 부르지 않는다.

## ADR-039: 어느 화면에서나 🚌 버튼으로 버스 검색

- **결정**: 모든 화면 오른쪽 위, ☰ 왼쪽에 🚌 버튼을 둔다. 누르면 "버스 검색" 화면(`#buses`)이 열린다.
  - 열리면 바로 번호를 칠 수 있게 입력에 포커스를 줘서 키패드를 띄운다.
  - 노선을 고르면 노선 정보 화면으로 간다.
  - 검색은 ADR-038의 `RouteFinder`/`searchRoutes`를 그대로 쓴다.
- **세부**:
  - 버스 검색 화면에서는 🚌 버튼을 숨긴다.
  - 노선 화면에서 뒤로 오면 마지막 검색어와 결과를 그대로 보여 준다(모듈 변수). 이때는 키패드가 결과를 가리지 않게 포커스를 주지 않는다.
  - 입력을 누르면 전체 선택돼서 바로 새 번호를 칠 수 있다.
  - 상단 바 오른쪽 여백은 52px에서 104px로 늘린다.
- 홈의 "버스 노선 바로 보기"(ADR-038)는 그대로 둔다.

## ADR-040: 공공데이터 API 호출 더 줄이기

경로 검색 결과의 자동 갱신이 도착정보 호출의 대부분이었다. 정확도를 크게 해치지 않는 선에서 아래 네 가지를 적용한다.

1. **자동 갱신 때 하차 정류장은 최근 값 재사용**
   - 하차 정류장 도착정보는 "탄 버스(차량 번호)가 언제 내릴 곳에 닿는지" 맞추는 데만 쓴다.
   - 자동 갱신 때는 3분(`ALIGHT_REUSE_MS`) 안에 받은 값이 있으면 다시 부르지 않는다(`peekArrivals`). 남은 시간은 받은 시각 기준으로 빼서 계산하므로 지난 값도 쓸 수 있다.
   - 첫 조회와 수동 새로고침(↻)은 전부 새로 받는다.
   - 즐겨찾기 카드에도 같은 규칙을 적용한다.
2. **경로 검색 결과 자동 갱신 30초 → 60초**: 같은 화면의 출발 정류장 도착판도 60초로 맞춘다. 남은 시간은 화면에서 1초마다 줄어든다. 즐겨찾기 상세와 노선 화면은 30초 그대로 둔다.
3. **Worker 도착정보 공유 캐시 20초 → 30초**
   - 저장할 때 `X-Fetched-At`을 붙이고, 캐시에서 꺼낼 때 `X-Data-Age`(초)를 알린다.
   - 웹은 받은 시각에서 그만큼 빼서 기준 시각으로 삼는다. 그래서 캐시가 길어져도 남은 시간이 부풀지 않는다.
4. **날씨는 기상청 발표 단위로 캐시**
   - 초단기실황(매시)과 단기예보(3시간마다) 원자료를 발표 시각이 든 키로 캐시한다(`kma/<op>/<격자>/<발표시각>`).
   - 요약은 요청 때마다 지금 시각으로 다시 계산한다.
   - 격자당 기상청 호출: 시간당 12회 → 약 1.3회.

**로컬 확인 결과** (서현역 → 판교역): 첫 조회는 도착정보 6회 호출. 60초 뒤 자동 갱신은 1회(출발 정류장만). 이전에는 30초마다 최대 6회였다.

**참고**: `*.workers.dev` 주소에서는 `caches.default`가 저장되지 않는 것으로 보인다(http.ts 주석). 그래서 공유 캐시는 사실상 같은 isolate 메모리 안에서만 겹친다. 커스텀 도메인을 붙이면 지역(데이터센터) 단위로 공유돼서 더 줄어든다.

## ADR-041: 요금을 보여 주고 요금도 고려해 정렬

- **배경**: 광역·직행좌석 버스는 일반 버스보다 약 2배 비싸다(3,200원 대 1,650원). 지금까지는 도착 시각만으로 정렬해서, 2분 빠른 광역버스가 일반 버스보다 앞에 왔다.
- **요금 추정** (`lib/fare.ts`, 성인·교통카드, 경기도 2025-10-25 인상 요금):
  - 기본요금과 기본거리:
    - 일반 1,650원, 10km
    - 마을 1,550원, 10km (시·군마다 다르며 성남 기준)
    - 좌석 2,650원, 30km
    - 직행좌석·광역급행 3,200원, 30km
  - 수도권 통합환승: 기본요금은 탄 버스 중 가장 비싼 것이고, 차액만 더 낸다. 거리는 전체 탑승거리(정류장 직선거리 합)로 본다. 기본거리를 넘으면 5km마다 100원을 더한다.
  - 직선거리라 실제와 몇백 원 다를 수 있어 "약"으로 표시한다.
  - 공항·시외버스는 통합환승 밖이라 "요금 별도"로 둔다.
  - 근거: 경기도 버스요금 안내(gg.go.kr), 2025-10-14 요금 인상 보도.
- **표시**: 결과 카드 오른쪽에 "약 1,950원"을 둔다. 좌석·직행·광역이 끼면 광역 색으로 강조한다. 상세 화면 요약에도 요금을 보여 준다.
- **정렬** (결과 위 세그먼트, 이 기기에 기억):
  - **추천(기본)**: 도착 시간 + 요금×0.6초로 정렬한다. 100원을 1분으로 보는 셈이라, 1,550원 더 비싼 광역버스는 15분 넘게 빨라야 앞에 온다.
  - **빠른 순**: 도착 시각 순.
  - **요금 적은 순**: 요금 순, 같은 요금이면 빠른 순.
  - 실시간 정보가 없는 경로는 어느 정렬이든 뒤로 간다. 요금을 모르는 경로는 5,000원으로 본다.
- **호출**: 정렬을 바꿔도 다시 조회하지 않게 후보를 전부(최대 12) 평가해 두고 화면에서 8개를 고른다. 자동 갱신(ADR-040)은 지금 보이는 순서의 위쪽 4개를 다시 본다.
- **환승**: 기존대로 직행과 1회 환승(도보 200m 이내 갈아타기)까지 찾는다. 2회 이상 환승은 찾지 않는다.

## ADR-042: 환승 후보가 비슷한 경로로 채워져 좋은 환승이 빠지던 문제

- **증상**: 서현역.분당우체국(07147) → 판교원마을1.2단지(07015)에서 "602 → 백현마을1단지 → 341·103" 환승이 나오지 않았다.
- **원인**: 이 경로는 후보로 만들어졌지만(정적 순위 9위), 실시간 평가로 넘기는 환승 후보 6개 안에 들지 못했다.
  - **첫 버스 대기시간이 정적 점수에 없었다.** 직행 후보와 환승의 두 번째 버스에는 평균 대기(배차의 절반)를 넣었는데 첫 버스에는 빠져 있었다. 그래서 하루 몇 번 안 다니는 버스(3500, P9901·P9902 퇴근)가 자주 오는 602와 같은 점수를 받았다.
  - **비슷한 후보가 자리를 다 차지했다.** "같은 정류장에서 반디4로 갈아타는" 경로가 첫 버스만 달리해 4개(602, 3500, P9901, P9902)가 들어갔다.
- **결정** (`findPlans`):
  1. 환승 첫 버스에도 평균 대기(배차×30초)를 더한다.
  2. 같은 정류장에서 같은 두 번째 버스로 갈아타는 후보는 가장 좋은 것 하나만 남긴다.
  3. 정적 점수에 요금도 넣는다. 일반버스보다 비싼 만큼을 100원 = 1분으로 환산한다(ADR-041 추천 정렬과 같은 기준). 그래서 광역·직행 후보가 일반버스 후보 자리를 덜 빼앗는다.
- **결과** (로컬, 실시간): 602→341이 21:13 도착으로 2위가 됐다. 직행인 누리3(21:19)보다 6분 빠르고 요금은 같다(1,650원, 마을→일반 환승). 602→103, 602→340도 후보에 든다.
- 실제 데이터 회귀 테스트를 `fulldata.test.ts`에 추가했다.
