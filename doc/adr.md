## ADR-001: 프런트엔드는 TypeScript + Vite
- 상태: 확정
- 날짜: 2026-11-18

**배경**
지도, 자동완성, 실시간 갱신이 있는 단일 페이지 웹앱이 필요하다. 정적 호스팅(ADR-003)에 올릴 수 있어야 한다.

**결정**
TypeScript와 Vite로 개발하고, 빌드 결과물(정적 파일)을 배포한다.

**결과**
- API 응답과 정류장 DB에 타입을 붙여 파싱 오류를 줄일 수 있다.
- Vite 빌드 결과는 GitHub Pages에 그대로 올릴 수 있다. 저장소 이름을 경로로 쓰므로 `base` 설정이 필요하다.
- UI 프레임워크(React/Vue/없음)는 아직 정하지 않았다. 필요하면 별도 ADR로 정한다.

<a id="adr-002"></a>
## ADR-002: 지도는 네이버 지도 JavaScript API
- 상태: 확정
- 날짜: 2026-11-18

**배경**
지도에서 정류장을 보고 클릭해서 출발지·도착지를 고를 수 있어야 한다 (FR-1.1).

**결정**
네이버 클라우드 플랫폼(NCP)의 Maps(Web Dynamic Map) API를 사용한다.

**결과**
- NCP에서 애플리케이션을 등록하고 Client ID를 받아야 한다.
- 서비스 URL(`https://<아이디>.github.io`, 개발용 `http://localhost:5173`)을 등록해야 지도가 뜬다.
- Client ID는 도메인으로 제한되므로 프런트엔드 코드에 넣어도 된다.
- 정류장이 많으므로 화면에 보이는 영역의 정류장만 표시하거나 마커를 묶어서(클러스터링) 표시해야 한다.
- 무료 사용량과 요금 조건은 NCP 가입 시 확인한다.

## ADR-003: 호스팅은 GitHub Pages
- 상태: 대체됨 → ADR-020 (2026-11-18)
- 날짜: 2026-11-18

**배경**
GitHub에서 코드를 관리하고 무료로 배포하려고 한다.

**결정**
프런트엔드 빌드 결과를 GitHub Actions로 GitHub Pages에 배포한다.

**결과**
- 비용 없이 HTTPS 주소(`https://<아이디>.github.io/<저장소>/`)를 얻는다.
- 정적 호스팅이라 서버 코드를 실행할 수 없다. 인증키 보호와 CORS 문제는 별도 프록시로 해결한다 (ADR-004).
- 정류장 DB(정적 JSON)도 같은 곳에서 제공한다 (ADR-006).

<a id="adr-004"></a>
## ADR-004: API 프록시로 Cloudflare Workers 사용
- 상태: 확정 (2026-11-18 검토 후 확정), 배포 방식과 CORS 부분은 ADR-020으로 변경
- 날짜: 2026-11-18

**배경**
- GitHub Pages는 정적 호스팅이라 브라우저가 data.go.kr을 직접 불러야 한다.
- 그러면 인증키가 브라우저 코드에 그대로 노출된다 (NFR-4 위반).
- (2026-11-18 확인) data.go.kr은 브라우저 직접 호출을 CORS로 막지 않는다. 따라서 프록시의 목적은 CORS가 아니라 키 보호와 공유 캐시다.
- 환승 검색은 정류장 여러 곳을 조회하므로 일일 호출 한도에 빨리 닿을 수 있다.

**결정**
Cloudflare Workers(무료 플랜)로 프록시를 만든다.
- 인증키는 Worker의 Secret에 저장한다.
- 브라우저는 Worker만 호출하고, Worker가 data.go.kr을 호출한다.
- 같은 정류장의 도착정보는 짧게 캐싱한다.
- CORS는 GitHub Pages 도메인과 localhost만 허용한다.
- NCP Geocoding·Reverse Geocoding도 같은 프록시로 중계한다 (ADR-013, ADR-019).
- 도착정보 캐시는 20초로 한다 (ADR-015).

**검토한 대안**
- GitHub Pages에서 브라우저가 직접 호출 (2026-11-18 재검토): data.go.kr은 다른 사이트에서의 브라우저 호출을 막지 않고(CORS 허용 확인), 네이버 주소 검색도 지도 JS API의 geocoder 모듈로 비밀키 없이 쓸 수 있어 기술적으로는 가능하다. 그러나 data.go.kr 인증키가 공개되어 다른 사람이 일일 호출 한도를 써 버릴 수 있고(텔레그램 봇도 같은 키 사용), 사용자 간 공유 캐시를 둘 수 없어 → 제외
- Vercel / Netlify Functions: 가능하지만 GitHub Pages와 따로 운영해야 하는 점은 같다. 무료 호출량과 응답 속도 면에서 Workers가 유리하다.

**결과**
- 무료 플랜: 하루 10만 요청, 요청당 CPU 10ms. Worker가 data.go.kr·네이버를 부르는 하위 요청은 요금에 세지 않는다 (2026-11-13 기준 공식 가격 문서).
- 예상 사용량(사용자 1명이 결과 화면을 1시간 켜 두면 약 360~600건)으로 보면 무료 플랜으로 충분하다. 무료 플랜에서 한도를 넘었을 때의 동작(요청 실패 여부)과 카드 등록 필요 여부는 가입 시 확인한다.
- 실제로 먼저 닿을 한도는 data.go.kr 일일 호출 한도이며, Worker의 공유 캐시가 이를 줄여 준다.
- Cloudflare 계정이 필요하다.
- 프런트엔드는 프록시 주소만 알면 된다.

## ADR-005: 데이터는 data.go.kr 경기도 버스 API
- 상태: 확정
- 날짜: 2026-11-18

**배경**
실시간 도착 정보와 경로 탐색용 정류장·노선 데이터가 필요하다.

**결정**
공공데이터포털(data.go.kr)의 경기도 버스 API를 사용하고, 텔레그램 봇에서 쓰던 인증키를 그대로 쓴다.

| 용도 | 서비스 | 상태 |
|---|---|---|
| 실시간 도착 | 경기도_버스도착정보 조회 (`busarrivalservice/v2`) | 승인됨 |
| 정류장 목록·좌표 | 경기도_정류소 조회 (`busstationservice/v2`) | 활용신청 필요 |
| 노선 정보, 노선별 정류장 순서 | 경기도_버스노선 조회 (`busrouteservice/v2`) | 활용신청 필요 |
| 버스 위치 (선택) | 경기도_버스위치정보 조회 (`buslocationservice/v2`) | 선택 |

**결과**
- 도착정보 API만으로는 경로를 찾을 수 없으므로 정류소·노선 서비스의 활용신청이 반드시 필요하다.
- 인증키는 하나지만 서비스마다 따로 승인을 받아야 한다.
- Encoding 키가 이중 인코딩되지 않도록 처리해야 한다 (텔레그램 봇에서 겪은 403 문제).
- 서울 버스·서울 정류장은 범위에서 빠진다.

<a id="adr-006"></a>
## ADR-006: 정류장 DB는 정적 JSON, GitHub Actions로 갱신
- 상태: 확정 (2026-11-18 검토 후 확정)
- 날짜: 2026-11-18

**배경**
- 자동완성과 지도 표시를 위해 정류장 전체 목록이 브라우저에 있어야 한다 (FR-1, FR-2).
- 경로 탐색에는 노선별 정류장 순서가 필요하다.
- 무료 정적 호스팅만 쓰므로 별도 DB 서버를 두지 않는다.

**결정**
- 빌드 스크립트(Node/TypeScript)가 정류소·노선 API를 호출해 정적 JSON을 만든다.
  - `stations.json`: stationId, 정류장 번호, 이름, 좌표, 경유 노선
  - `routes.json`: routeId, 노선 번호, 정류장 순서
- GitHub Actions가 이 스크립트를 정기 실행하고(주기는 ADR-016), 바뀐 내용이 있으면 다시 배포한다. 수동으로도 실행할 수 있다.
- 브라우저는 처음 열 때 JSON을 받아 캐시하고, 자동완성 인덱스를 메모리에서 만든다.

**결과**
- 서버나 DB 비용이 없다.
- 파일 크기는 지역 범위(ADR-010)에 따라 달라진다. 크면 지역별로 나누거나 압축해서 제공한다.
- 노선 API를 노선마다 호출해야 하므로 처음 수집할 때 호출이 많다. 일일 한도를 고려해 나눠서 수집하거나 이전 결과와 비교해 바뀐 노선만 갱신한다.
- 인증키는 GitHub Actions Secret에 저장한다.

<a id="adr-007"></a>
## ADR-007: 저장은 브라우저 localStorage
- 상태: 확정
- 날짜: 2026-11-18

**배경**
선택한 출발지·도착지와 즐겨찾기 노선을 저장해야 한다 (FR-3, FR-5). 로그인 기능은 없다.

**결정**
브라우저 localStorage에 JSON으로 저장한다. 저장 형식에 버전 번호를 넣어 나중에 형식이 바뀌어도 변환할 수 있게 한다.

**결과**
- 서버가 필요 없다.
- 기기와 브라우저마다 따로 저장된다. 다른 기기와 동기화되지 않는다.
- 브라우저 데이터를 지우면 함께 지워진다.
- 사생활 보호 모드처럼 localStorage를 쓸 수 없는 경우에도 앱은 동작해야 한다(저장만 안 됨).

<a id="adr-008"></a>
## ADR-008: 탑승 시간 추정 방식
- 상태: 확정 (2026-11-18 검토 후 확정)
- 날짜: 2026-11-18

**배경**
- 경로의 도착 시각을 계산하려면 승차 정류장에서 하차(또는 환승) 정류장까지의 탑승 시간이 필요하다 (FR-4.3, FR-4.4).
- 경기도 API는 정류장 간 소요 시간을 직접 주지 않는다.
- 도착정보 API는 정류장마다 노선별 다음 버스 2대의 예측 시간과 차량번호(`plateNo1/2`)를 준다.

**결정**
아래 순서로 추정한다.
1. **차량 추적:** 내가 탈 버스의 차량번호가 하차 정류장의 도착 예측에도 나오면, 그 예측 시간을 하차 시각으로 쓴다. 가장 정확하다.
2. **구간 평균:** 1이 안 되면 (정류장 수 × 평균 구간 시간) 또는 (노선 거리 ÷ 평균 속도)로 추정한다. 평균값은 실측으로 조정한다.
3. 2번 방식으로 계산한 값은 화면에 "추정"으로 표시한다 (FR-4.6).

환승 정류장 대기 시간은 이렇게 계산한다.
- 환승 정류장 도착 시각 + 도보 시간 이후에 오는 다음 버스를 실시간 예측에서 찾는다.
- 예측 2대 안에 없으면 배차 간격으로 추정하고 "추정"으로 표시한다.

**결과**
- 하차 정류장의 도착정보를 추가로 조회해야 해서 API 호출이 늘어난다. 프록시 캐시로 줄인다 (ADR-004).
- 먼 구간은 대부분 2번 방식(추정값)이 된다.

<a id="adr-009"></a>
## ADR-009: 경로 정렬은 최종 도착 시각 우선
- 상태: 확정
- 날짜: 2026-11-18

**배경**
직행과 환승 경로를 함께 보여 줄 때 어떤 순서로 보여 줄지 정해야 한다. 요구사항: "갈아타더라도 가장 빨리 도착하는 것을 우선순위 높여 보여줘".

**결정**
- 1순위: 최종 도착 예정 시각이 빠른 순
- 2순위(도착 시각이 같을 때): 환승 횟수가 적은 순
- 3순위: 걷는 시간이 짧은 순
- 사용자는 **직행만** / **환승 포함** 모드를 고를 수 있다 (FR-4.1).

**결과**
- 환승 경로가 직행보다 빠르면 위에 나온다.
- 추정값이 들어간 경로도 같은 기준으로 정렬하되, 추정값임을 표시한다.

<a id="adr-010"></a>
## ADR-010: 서비스 지역은 성남시부터 시작
- 상태: 확정 (D-01)
- 날짜: 2026-11-18

**배경**
경기도 전체 정류장은 수만 개이고, 노선별 정류장 순서를 모으려면 노선마다 API를 호출해야 한다. 개발계정의 일일 호출 한도 안에서 처음 수집을 끝내고, DB 파일도 작게 유지하고 싶다. 지금 쓰는 정류장(판교·서현·백현)은 모두 성남시에 있다.

**결정**
- 정류장 DB는 **성남시 정류장**만 담는다.
- 노선 DB는 **성남시 정류장을 하나라도 지나는 노선**을 담는다. 노선의 정류장 순서는 성남 밖 구간까지 전체를 저장한다.
- 지역 목록은 설정값으로 두어 나중에 다른 시(용인 등)를 추가할 수 있게 한다.

**결과**
- 출발지·도착지는 성남시 정류장만 고를 수 있다.
- 노선이 성남 밖으로 나가도 경로 계산에는 노선 전체 순서를 쓴다. 다만 성남 밖 정류장은 지도와 자동완성에 나오지 않는다.
- 환승도 성남시 정류장에서만 찾는다.
- 지역을 넓히면 DB 크기와 처음 수집 시간이 늘어난다 (ADR-006).

<a id="adr-011"></a>
## ADR-011: 최대 환승은 1회
- 상태: 확정 (D-02)
- 날짜: 2026-11-18

**배경**
환승 횟수가 늘수록 경로 후보와 실시간으로 조회할 환승 정류장이 크게 늘어난다. 실시간 예측은 다음 버스 2대까지만 있어서, 환승을 여러 번 하면 뒤쪽 구간은 대부분 추정값이 된다 (ADR-008).

**결정**
경로 탐색은 **직행**과 **1회 환승**까지만 한다.

**결과**
- 경로 후보 = (출발 정류장 노선 × 도착 정류장 노선)의 공통·인접 정류장 조합이므로 미리 계산한 노선 DB만으로 빠르게 찾을 수 있다.
- 실시간 조회는 출발 정류장, 환승 정류장, (차량 추적용) 하차 정류장으로 한정된다.
- 1회 환승으로 갈 수 없는 출발지·도착지 쌍은 "경로 없음"으로 안내한다.

<a id="adr-012"></a>
## ADR-012: 환승 도보는 반경 200m까지 허용
- 상태: 확정 (D-03)
- 날짜: 2026-11-18

**배경**
실제 환승은 내린 정류장이 아니라 길 건너편이나 옆 블록 정류장에서 하는 경우가 많다. 같은 정류장만 허용하면 이런 경로를 놓친다.

**결정**
- 하차 정류장에서 **직선거리 200m 안**의 정류장을 환승 후보로 본다 (같은 정류장 포함).
- 도보 시간 = 직선거리 × 1.3(실제 보행 경로 보정) ÷ 보행 속도 1.2m/s, 최소 1분으로 계산한다.
- 계산한 도보 시간은 경로 결과에 따로 표시한다 (FR-4.4).
- 반경과 보정 계수는 설정값으로 둔다.

**결과**
- 근처 정류장 쌍(200m 이내)은 정류장 DB를 만들 때 미리 계산해 저장한다 (ADR-006).
- 도보 시간은 추정값이다. 횡단보도 신호 대기 등은 반영되지 않는다.
- 출발지·도착지가 주소·장소일 때 근처 정류장까지 걷는 구간은 ADR-013에서 다룬다.

<a id="adr-013"></a>
## ADR-013: 출발지·도착지에 주소·장소 검색 포함
- 상태: 확정 (D-04), 장소 이름 검색 부분은 ADR-019로 변경
- 날짜: 2026-11-18

**배경**
사용자는 정류장 이름을 모르는 경우가 많다. "판교역", "회사 주소"처럼 주소나 장소 이름으로 출발지·도착지를 정할 수 있어야 편하다.

**결정**
- 입력창 자동완성은 **정류장**(정류장 DB)과 **주소·장소**(네이버 API) 결과를 함께 보여 주고, 종류를 아이콘으로 구분한다.
  - 장소 이름: 네이버 검색 API의 지역 검색
  - 주소: NCP Maps의 Geocoding API
- 지도에서 정류장이 아닌 곳을 길게 누르거나 클릭해도 그 위치를 출발지·도착지로 지정할 수 있다 (좌표 → 주소 표시는 NCP Reverse Geocoding).
- 출발지·도착지가 주소·장소이면 **반경 500m 안의 정류장**을 승차·하차 후보로 쓰고, 걷는 시간을 경로 시간에 더한다. 걷는 시간 계산은 ADR-012와 같은 방식이다.
- 위 네이버 API들은 Client Secret이 필요하므로 **API 프록시(ADR-004)를 거쳐서** 호출한다.
- 주소·장소 검색은 입력이 2글자 이상이고 입력을 멈춘 뒤(약 300ms) 호출해서 호출 수를 줄인다.

**결과**
- 네이버 개발자센터(검색 API)와 NCP(Geocoding, Reverse Geocoding) 사용 신청이 추가로 필요하다.
- 프록시가 data.go.kr뿐 아니라 네이버 API도 중계하게 되므로 ADR-004를 확정해야 한다.
- 출발지·도착지 후보 정류장이 여러 개가 되어 경로 후보와 실시간 조회가 늘어난다. 후보 정류장은 가까운 순으로 개수를 제한한다(예: 각 5개).
- 서비스 지역 밖(성남시 밖, ADR-010) 주소는 "지원 지역 밖"으로 안내한다.
- 저장하는 출발지·도착지(FR-3)에는 종류(정류장/장소)와 좌표를 함께 저장한다.
- 반경 500m와 후보 개수는 설정값으로 둔다.

## ADR-014: 화면은 모바일 우선
- 상태: 확정 (D-05)
- 날짜: 2026-11-18

**배경**
버스를 기다리거나 나가기 직전에 확인하는 서비스라 주로 휴대폰에서 쓴다.

**결정**
- 휴대폰 세로 화면(폭 360~430px)을 기준으로 설계한다.
  - 지도는 화면 위쪽에, 검색·결과·즐겨찾기는 아래에서 끌어올리는 패널(바텀 시트)로 둔다.
  - 버튼과 목록 항목은 손가락으로 누르기 쉬운 크기(최소 44px)로 한다.
- 화면이 넓으면(폭 768px 이상) 왼쪽에 패널, 오른쪽에 지도를 나란히 배치한다.
- 홈 화면에 추가해서 앱처럼 열 수 있도록 웹 앱 매니페스트를 제공한다. 오프라인 기능은 범위에 넣지 않는다.

**결과**
- 결과 목록은 한 줄에 핵심 정보(도착 시각, 총 소요 시간, 환승 여부)만 보여 주고, 눌러서 상세(구간별 시간)를 펼친다.
- 지도 마커와 자동완성 목록도 터치 조작을 기준으로 만든다.

<a id="adr-015"></a>
## ADR-015: 실시간 정보 자동 갱신은 30초
- 상태: 확정 (D-06)
- 날짜: 2026-11-18

**배경**
실시간 도착 예측은 자주 바뀌지만, 너무 자주 부르면 같은 값을 다시 받으면서 일일 호출 한도만 쓴다.

**결정**
- 결과 화면이나 즐겨찾기 화면을 보고 있을 때 **30초마다** 실시간 정보를 다시 불러온다.
- 다시 불러오는 사이에는 화면의 남은 시간을 **1초마다 줄여서** 보여 준다.
- 브라우저 탭이 안 보이는 동안(백그라운드)은 갱신을 멈추고, 다시 보이면 바로 갱신한다.
- 수동 새로고침 버튼은 언제든 쓸 수 있다. 다만 프록시 캐시 때문에 같은 정류장은 최대 20초 동안 같은 값이 나올 수 있다.
- 프록시의 도착정보 캐시는 **20초**로 한다 (ADR-004).

**결과**
- 사용자 한 명이 화면을 켜 두면 정류장당 분당 2회 정도 호출한다. 여러 사람이 같은 정류장을 보면 프록시 캐시 덕분에 호출이 늘지 않는다.
- 마지막 갱신 시각을 화면에 표시한다.

<a id="adr-016"></a>
## ADR-016: 정류장 DB는 매주 자동 갱신 + 수동 실행
- 상태: 확정 (D-07)
- 날짜: 2026-11-18

**배경**
노선 개편이나 정류장 신설은 자주 일어나지 않는다. 반면 노선별 정류장 순서를 모으려면 노선마다 API를 불러야 해서, 매일 수집하면 일일 호출 한도를 많이 쓴다.

**결정**
- GitHub Actions로 **매주 1회**(월요일 새벽, 한국 시간 03:00) 정류장·노선 데이터를 다시 수집한다.
- GitHub 화면에서 **수동 실행**(workflow_dispatch)도 할 수 있게 한다.
- 수집 결과를 이전 데이터와 비교해 **바뀐 내용이 있을 때만** 커밋하고 다시 배포한다.
- 수집이 실패하거나 결과가 비정상적으로 작으면(예: 정류장 수가 이전보다 20% 넘게 줄면) 기존 데이터를 유지하고 실패로 표시한다.

**결과**
- 노선 개편은 최대 1주일 늦게 반영될 수 있다. 급하면 수동으로 실행한다.
- 데이터에 수집 날짜를 넣어 화면에 "정류장 정보 기준일"로 표시한다.
- GitHub Actions 무료 사용량 안에서 충분히 돌아간다.

<a id="adr-017"></a>
## ADR-017: 즐겨찾기는 경로 전체 단위
- 상태: 확정 (D-08)
- 날짜: 2026-11-18

**배경**
추천 결과에서 고른 노선을 즐겨찾기로 저장해야 한다 (FR-5). 환승 경로는 노선이 2개이고 승차·환승·하차 정류장이 각각 다르다.

**결정**
- 즐겨찾기 하나 = **경로 하나 전체**: 출발지 → (승차 정류장, 노선) → [환승 정류장, 노선] → 하차 정류장 → 도착지.
  - 예: "판교 → 서현: 32번 → 백현마을1단지 환승 → 103번"
- 즐겨찾기를 누르면 그 경로만 실시간으로 다시 계산해서 보여 준다.
  - 각 구간의 실시간 도착 예정 시간
  - 환승 대기 시간, 최종 도착 예정 시각
- 이름을 바꿀 수 있다 (예: "출근").
- 저장 형식에는 stationId, routeId와 표시용 이름·번호를 함께 넣는다. 노선이 없어지는 등 DB에서 찾을 수 없게 되면 "노선 정보가 바뀌었습니다"로 표시한다.

**결과**
- 즐겨찾기 화면에서 경로마다 "다음 출발 가능 시각"과 "도착 예정 시각"을 한 줄로 보여 줄 수 있다.
- 같은 출발지·도착지의 다른 경로와 비교하려면 저장된 출발지·도착지 쌍(FR-3)으로 다시 검색한다.

## ADR-018: 웹서비스는 새 GitHub 저장소에 둔다

**배경**
기존 `C:\Claude\mybus` 폴더에는 텔레그램 봇 코드와 `.env`(실제 키)가 있고, git 저장소가 아니다. 웹서비스는 GitHub Pages로 공개 배포한다 (ADR-003).

<a id="adr-019"></a>
## ADR-019: 네이버 검색 API는 쓰지 않고 주소 검색만 사용
- 상태: 확정 (ADR-013 일부 변경)
- 날짜: 2026-11-18

**배경**
ADR-013에서는 장소 이름 검색에 네이버 검색 API(지역 검색)를 쓰기로 했다. 신청하고 관리할 API를 줄이기 위해 이 API는 쓰지 않기로 했다.

**결정**
- 네이버 검색 API(지역 검색)는 사용하지 않는다.
- 입력창 자동완성은 **정류장**(정류장 DB)과 **주소**(NCP Geocoding) 두 가지만 보여 준다.
- 지도에서 위치를 눌러 지정하는 기능(NCP Reverse Geocoding)과 근처 500m 정류장 검색, 도보 시간 계산은 ADR-013대로 유지한다.

**결과**
- "스타벅스 판교점", "회사 이름" 같은 **장소 이름으로는 검색되지 않는다.** 이런 곳은 주소로 검색하거나 지도에서 직접 눌러야 한다.
- 다만 "판교역", "서현역", "분당구청"처럼 **정류장 이름에 들어 있는 장소**는 정류장 자동완성으로 찾을 수 있다.
- 신청할 API에서 네이버 개발자센터(검색 API)가 빠진다. NCP Maps(지도, Geocoding, Reverse Geocoding)만 있으면 된다.
- NCP Geocoding은 도로명·지번 주소 입력에 맞춰져 있으므로, 자동완성은 입력이 주소 형태일 때(예: 숫자나 "로/길/동"이 들어 있을 때) 우선으로 호출한다.

<a id="adr-020"></a>
## ADR-020: 웹 화면과 API를 모두 Cloudflare Workers 하나로 배포
- 상태: 확정 (ADR-003 대체, ADR-004 일부 변경)
- 날짜: 2026-11-18

**배경**
ADR-003은 웹 화면을 GitHub Pages에, ADR-004는 API 프록시를 Cloudflare Workers에 두는 구성이었다. 배포 위치가 두 곳이라 관리할 곳이 많고, 서로 다른 주소라 CORS 설정이 필요했다. Cloudflare Workers는 정적 파일 제공이 무료이고 요청 수 제한도 없다.

**결정**
- Worker 하나(`mybus-route`)가 **웹 화면(정적 파일)과 API를 함께** 제공한다.
  - `/api/*` 요청은 Worker 코드가 처리한다 (도착정보, Geocoding).
  - 나머지 요청은 `web/dist`의 정적 파일로 응답한다 (Workers Static Assets).
- 웹과 API가 같은 주소를 쓰므로 **CORS 설정을 없앤다.** 로컬 개발에서는 Vite 개발 서버가 `/api`를 로컬 Worker로 넘긴다.
- 배포는 Cloudflare의 **Workers Builds**를 GitHub 저장소에 연결해서 `main`에 push할 때마다 자동으로 한다. GitHub Pages 배포 워크플로는 지운다.
- GitHub 저장소는 코드 보관용이며 **Public을 유지**한다 (2026-11-18 결정). 나중에 Private으로 바꿔도 배포에는 영향이 없다.

**결과**
- 서비스 주소: `https://mybus-route.<Cloudflare 계정 서브도메인>.workers.dev` (나중에 도메인을 붙일 수 있다).
- 네이버 지도(NCP) 서비스 URL에는 위 주소와 `http://localhost:5173`을 등록한다 (ADR-002).
- Vite `base`는 `/`가 된다 (ADR-001).
- 네이버 지도 Client ID는 빌드할 때 넣으므로 Workers Builds의 빌드 변수(`VITE_NAVER_MAP_CLIENT_ID`)로 등록한다.
- 정류장 DB 주간 갱신(ADR-016)은 계속 GitHub Actions로 실행하고, 결과를 커밋하면 Workers Builds가 다시 배포한다.
- 정적 파일 요청은 무료이고 Worker 요청 수(하루 10만)에 세지 않는다. `/api/*` 요청만 센다.
